| 023 | 2026-09-03 | `cost_events.id`/`risk_history.id` are `NULLABLE` in BigQuery, not `REQUIRED` as first written | Make every BQ column mirror its Postgres `NOT NULL`/PK exactly | Both are Postgres `bigserial` primary keys with no meaning outside Postgres. `packages/ledger/bq_stream.py`'s streaming cost_events path (near-real-time spend visibility, distinct from the nightly full mirror) can't supply one client-side, so `REQUIRED` would make every streamed row fail. Separately, `bq_sync.py`'s first live run against real BigQuery failed with `400 Unsupported empty struct type for field 'ref'` — BigQuery's JSON-from-NDJSON loader rejects an empty dict (`{}`) for a `JSON`-typed column even though the destination schema is already fixed; fixed by mapping empty dicts to `null` before upload (semantically equivalent for our data). Both caught by actually running the sync and streaming paths against real BigQuery, not just `terraform plan`. See `docs/evidence/02-bigquery.md`. |
| 024 | 2026-09-03 | `bq_sync.py`'s `LoadJobConfig` must pass `schema=bq_client.get_table(table_ref).schema, autodetect=False` explicitly | Trust `write_disposition`/`source_format` alone to leave the destination schema untouched | A more serious sequel to #023: after that first successful sync, `terraform plan` started showing `evidence` and `verification_history` needing full replacement — their `output`/`basis`/`ref` columns had silently turned from `JSON` into nested `RECORD` in the *real* BigQuery schema. The load job, given no explicit schema, inferred each JSON column's shape from that run's actual row data and rewrote the live table schema to match, out from under Terraform entirely — a load job without a pinned schema is not the read-only-shape-wise operation it looks like. Fixed by fetching and passing the destination table's existing schema into every load job. Verified by restoring the two tables via `terraform apply`, rerunning the sync with the fix, and confirming `terraform plan` then showed no diff. **Action for any future code that writes to a table Terraform also owns: always pin the schema explicitly, never rely on an implicit "existing schema" behavior.** |
