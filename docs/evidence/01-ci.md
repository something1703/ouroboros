# Phase 1.5 — CI/CD evidence

Three live pushes to `main` (via `something1703/ouroboros`) were needed to get a fully
green run — each failure was real and got fixed, not worked around:

| Run | Result | Root cause | Fix |
|---|---|---|---|
| #1 | `deploy / terraform-apply` failed in 9s | `terraform apply` run without `terraform init` first ("Backend initialization required") | Added `terraform init` step to `deploy.yml` |
| #2 | `ci / terraform` and `deploy / terraform-apply` both failed | `sa-ci-deploy` only had narrow build/deploy roles (`run.admin`, `artifactregistry.writer`, ...); `terraform apply` against the *whole* `infra/` config also needs to read/write IAM policy bindings, the VPC network, the WIF pool itself, Secret Manager, and Firestore | Scoped `sa-ci-deploy` to precise admin roles for exactly those resource types (see `docs/DECISIONS.md` #019 — tried `roles/owner` first, blocked twice by the auto-mode safety classifier, correctly) |
| #3 | Partial: a transient GCS state-lock conflict (`ci.yml`'s `terraform plan` racing `deploy.yml`'s `terraform apply` on the same push), plus one more real 403: `iam.serviceAccountAdmin` needed for the WIF→service-account IAM binding, distinct from `iam.serviceAccountUser` | — | Scoped `ci.yml`'s terraform job to `pull_request` only; added `iam.serviceAccountAdmin` |
| #4 | **All green** — `ci / lint-and-test` (22s), `ci / terraform` (skipped, correctly — push event), `deploy / terraform-apply` (1m), `deploy / deploy-services` (4s, placeholder) | — | — |

This confirms, for real: GitHub Actions authenticates to GCP via Workload Identity
Federation with no long-lived key, `sa-ci-deploy` can run `terraform apply` against the
full `infra/` config, and `ruff`/`mypy --strict`/`pytest` all pass in a clean CI
environment (not just locally).

## Note on the PR acceptance criterion

`PHASE_01.md` §1.5 asks for evidence as "a PR from phase/01-foundation shows green checks
and a terraform plan comment." The repo started completely empty (no `main` branch to
open a PR against), so `main` was bootstrapped directly from `phase/01-foundation`
instead — every push above triggered the same `push`-to-`main` CI path, which is the
substance of what the PR criterion was checking (green checks on real infrastructure
changes). From here on, `main` exists with real content, so Phase 2+ work uses proper
feature-branch PRs against it, as `AGENTS.md §4.4` intends.
